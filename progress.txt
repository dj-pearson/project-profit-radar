## Consolidated Patterns

### Supabase Query Patterns
- Client: `src/integrations/supabase/client.ts` - createClient with env vars
- Types: `src/integrations/supabase/types.ts` (manually maintained, not auto-generated)
- All queries use RLS (Row Level Security) with company_id isolation
- Pattern: `const { data, error } = await supabase.from('table').select('*').eq('company_id', companyId)`
- Mutations wrapped in TanStack Query: `useMutation({ mutationFn: async () => { ... } })`
- Data fetching hooks use `useQuery` with `enabled: !!user` guard

### Component Architecture
- shadcn/ui components in `src/components/ui/` (Radix UI primitives + Tailwind)
- Domain components organized by feature directory (117+ directories)
- Functional components with hooks only (no class components)
- State: React Context for global (auth, theme), TanStack Query for server state
- Styling: Tailwind CSS with `cn()` utility from `src/lib/utils.ts`
- Import alias: `@/` maps to `src/`

### Authentication & Authorization
- AuthContext at `src/contexts/AuthContext.tsx` - provides `useAuth()` hook
- 6 roles: admin, project_manager, field_supervisor, office_staff, accounting, client_portal
- Route guards: `SecureRoute` component with `allowedRoles` prop
- JWT tokens via Supabase Auth
- ProtectedRoute has circuit-breaker logic for redirect loops

### Routing
- React Router DOM 6.26.2 with lazy loading
- `createLazyRoute()` in `src/utils/lazyRoutes.tsx` wraps routes with Suspense + RouteErrorBoundary
- Route files: appRoutes, financialRoutes, projectRoutes, peopleRoutes, operationsRoutes, marketingRoutes
- Admin pages use `DashboardLayout` wrapper
- Nav config: `src/components/navigation/HierarchicalNavigationConfig.ts`

### Testing Patterns
- Unit: Vitest 4.0.8 + Happy DOM + Testing Library
- E2E: Playwright 1.56.1 (Chromium, Firefox, WebKit)
- Test setup: `src/test/setup.ts`
- A11y testing: `src/test/accessibility-utils.ts` with axe-core
- Coverage: V8 provider, 60% thresholds configured but actual coverage <2%
- Mock Supabase client for unit tests (no real API calls)

### Build & Deploy
- Vite 5.4.1 with manual chunking, tree shaking, code splitting
- Build: `npm run build` (includes sitemap gen, 404 copy, SW version update, image optimization)
- Deploy: Cloudflare Pages from `dist/` folder
- TypeScript: `tsconfig.app.json` covers `src/`, `tsconfig.node.json` covers config files
- `package.json` has `"type": "module"` - CommonJS scripts need `.cjs` extension
- Edge functions are Deno (TypeScript) - NOT checked by `tsc --noEmit`

### Known Pitfalls
- Self-hosted Supabase: foundational tables (user_profiles, companies) may not exist
- Migrations must be idempotent: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`
- RLS policies referencing `get_user_role()` fail if function doesn't exist - use `auth.uid() IS NOT NULL`
- Env vars must be ALL_CAPS_SNAKE_CASE (previously had mixed-case bugs)
- ~65 unique env vars needed across edge functions
- tsconfig.json extends `expo/tsconfig.base` - root config has Expo integration
- TOAST_LIMIT was 1 (caused dropped notifications) - now set to 5

## 2026-06-27 - CORRECTION: US-212 / tsconfig regression reverted

### What happened

`ignoreDeprecations "6.0"`. The repo PINS `typescript@^5.9.2`, which:
  1. does NOT treat `baseUrl` as a hard deprecation error (no TS5101), and
  2. REJECTS `"6.0"` as an invalid value → `error TS5103: Invalid value for '--ignoreDeprecations'`.

So the edit was unnecessary AND turned the typecheck failure into a different (config) failure.

### Verified via GitHub Action (PRD Verification run 28299610938) + main CI history
- Build job: SUCCESS — `npm run build` passes (confirms the build-completion acceptance
  criterion for US-093 and US-133; those `passes: true` markings stand).

  fails (it ran ~39 min before failing on REAL type errors, not a config error). Therefore
  **US-212 is genuinely incomplete and remains passes: false** — the strict-mode error
  backlog is NOT burned down.
- main CI is broadly red anyway: Lint, Unit Tests, and E2E jobs also fail on `main`
  (corroborates US-213/214/215 and the quality-story backlog being incomplete).

### Action
Reverted the tsconfig.app.json change (removed the invalid ignoreDeprecations line). No

2026-08-27 — US-241 input validation: helper, guard, and the first six schemas
================================================================================

### The decision that shaped this: report mode, not enforce
CLAUDE.md's Security rule 2 says validate every input with Zod. Its Backward
Compatibility section says tightening an input schema is a never-in-one-release
change. Adding validation where there was none is exactly that tightening — an
iOS client at MIN_SUPPORTED_IOS_VERSION that sends a shape the new schema
rejects starts getting 400s and cannot update its way out. There is no staging
Supabase project to discover that on (US-247 is still open), and nobody knows
what shapes real traffic actually sends.

So _shared/validate-body.ts has two modes, switched by INPUT_VALIDATION_MODE on
the Supabase project:

  report (default) — parse, and on failure log
                     `[input-validation] <fn> would reject: <field paths>`
                     and hand the handler the RAW body. Behaviour unchanged.
  enforce          — parse, and on failure return 400 with the standard
                     { success:false, error, timestamp } envelope.

A body that is not JSON at all is rejected in both modes. That is a malformed
request, not a schema tightening, and the handler could not have used it either.

**The flip is an ops action, not a code change.** Ship schemas, watch the
`[input-validation]` lines for a full release cycle, fix the schemas that
legitimate clients trip, then set INPUT_VALIDATION_MODE=enforce.

### Schemas added (6 of ~30)
The ones the security audit named: change-orders (discriminated union over
list/create/update/approve/reject), geofencing (union over its five actions —
transcribed straight from the TS param types each handler already declares,
which document the contract exactly), change-subscription, generate-invoice,
execute-workflow, projects.

One typing note: a discriminated-union schema makes `parsed.data` a union, and
destructuring `const { action } = body` narrows the *variable*, not `body`. So
`body.project_id` inside `if (action === 'create')` would not compile. The
handlers keep a `Record<string, any>` cast with a comment saying why — the
schema is the runtime contract, and edge functions are not in tsconfig's
`include` (which is `["src"]`) so they were never typechecked by the repo's own
tooling anyway.

### Security finding: mass assignment in `projects`
Both handlers spread the raw body straight into the DB:

    const projectData = { ...body, company_id, created_by, ... }
    ...
    .update(body)

Every writable column on `projects` was therefore settable by the caller —
including `id`, `created_by`, `created_at`, `company_id`, `site_id`, `tenant_id`.

The cross-tenant move is blocked, and it is worth writing down why so nobody
"fixes" it wrong later: `projects_update` in 20260128000001_defense_in_depth_rls.sql
declares a USING clause and no WITH CHECK, and Postgres applies the USING
expression to the new row when WITH CHECK is absent. `initializeAuthContext`
builds its client with the ANON key plus the caller's Authorization header, so
RLS genuinely applies. A caller cannot move a project to another company.

What was not blocked: rewriting `created_by`, `created_at` or `id` inside your
own company. Both paths now go through an explicit column allowlist derived
from the generated types. That allowlist is applied **unconditionally**, not
staged behind INPUT_VALIDATION_MODE — dropping a column a client should never
have been writing is not the kind of narrowing that breaks an older client.

Worth a sweep of its own: other functions that spread a request body into a
Supabase write.

### The guard, and a bug in its first draft
scripts/check-edge-input-validation.mjs, wired into .husky/pre-commit and CI.

First version counted "functions calling req.json() that also have a schema" —
which reads zero after conversion, because a converted function stops calling
req.json() at all (validateBody reads it). Converted functions silently vanished
from both numerator and denominator. Now it counts anything that takes a JSON
body (reads it raw OR calls the helper) and splits on whether a schema is
involved. 23 validated, 133 backlog, of 156.

2026-08-27 — US-241 mass-assignment sweep: two real findings
================================================================================

Swept every edge function with the TypeScript AST for writes that spread a
request body into insert()/update()/upsert(). The first pass found one site; it
only tracked variables bound *directly* from req.json(), so a body copied into
another variable slipped past. Following aliases to a fixpoint — `const x = body`,
`const y = { ...body }`, `const z = body as T` — surfaced the second.

Script pattern, worth keeping: collect body-derived names, grow that set until
it stops changing, then walk every CallExpression whose property name is
insert/update/upsert and scan its first argument for an identifier in the set
(recursing through array literals and spread assignments). It generalises to any
"tainted value reaches sink" question in this repo.

### Finding 1 — api-management, service role, cross-tenant write
POST /api/projects on the third-party API. It builds its client with
SUPABASE_SERVICE_ROLE_KEY, so **RLS is not a backstop** — whatever the body
carries reaches Postgres. It spread the body and overrode `company_id`, but not
`site_id` or `tenant_id`. An API-key holder could write a project into another
tenant's site, and set `id`, `created_by` and `created_at` on the way.

`site_id` now comes from `companies.site_id` for the key's own company. The API
key record only carries company_id, so that lookup is the only server-side
source; the request 400s if it does not resolve.

### Finding 2 — time-tracking, self-approving timesheets
The clock-in handler spread the body into `time_entries`. That table's RLS
(time_entries_insert in 20260128000001_defense_in_depth_rls.sql) checks
`user_in_company(company_id)` and that the row is your own — and nothing else.
So `approval_status`, `approved_by`, `approved_at`, `approval_notes`,
`rejection_reason` and `submitted_at` were all caller-settable. A worker could
clock in with `approval_status: 'approved'` and skip timesheet review entirely.
That is a payroll control, not a data-shape nit.

Those columns and `total_hours` are off the allowlist. `total_hours` is computed
from start/end by the stop handler anyway.

### The generalisation, filed as US-297
The RLS policies in this repo check *tenancy and ownership*. None of them
constrain *which columns* a role may write. So any table carrying workflow-state
or approval columns has this hole wherever a handler writes caller-supplied
fields, and any service-role function has it with no backstop at all.

### Why the allowlists could be applied immediately
Unlike the schemas, the allowlists are not staged behind INPUT_VALIDATION_MODE.
Dropping a column a client should never have been writing does not strand an
older client. Checked callers before narrowing anyway:

  projects        0 in-repo callers
  time-tracking   0
  geofencing      0
  api-management  3      (external API-key holders too — hence deriving site_id
                          rather than dropping it outright)
  change-orders   7
  generate-invoice 2
  execute-workflow 1
  change-subscription 1

projects, time-tracking and geofencing having no caller at all is its own
signal — more unwired surface, same family as the MFA stubs in US-296.

2026-08-27 — US-297 privilege-write audit: two real holes
================================================================================

90 edge functions build a service-role client; 41 of those read a request body
and write. Three AST sweeps over them.

### Finding 1 — free affiliate rewards (process-referral-signup)
verify_jwt = false, service-role client, so the entire body is
attacker-controlled. The handler took `subscription_tier` and
`subscription_duration_months` from that body, and

    if (subscription_duration_months >= minDuration) { ...mint rewards... }

was the *only* gate on inserting affiliate_rewards rows for both referrer and
referee. Anyone who knew an email with a pending referral — including their own,
after signing up through someone's link — could POST `{ subscription_duration_
months: 12 }` and mint rewards for a subscription that never existed. The reward
*amounts* come from the referral row, so the size was not attacker-controlled,
but the trigger was entirely. `referee_company_id` was also unverified and
becomes the company_id on the referee's reward.

Both facts now come from `subscribers` (subscribed / subscription_tier /
billing_period), and referee_company_id must match the referee's own profile.

### Finding 2 — cross-tenant billing writes (track-usage)
Took `company_id` and `user_id` from the body, falling back to the profile only
when absent. It uses a user-JWT client, so RLS applies — except `usage_metrics`
carries `CREATE POLICY "System can manage usage metrics" ON usage_metrics FOR
ALL USING (true)` (20250703170531_...sql), which is one of the 41 permissive
policies the pre-commit RLS audit already reports. That policy grants every
authenticated role full write access, so RLS was not scoping anything.

usage_metrics feeds usage-billing, calculate-usage-bill and
generate-usage-invoice. So any authenticated user could book usage against any
company's bill. Both values now come from the caller's own profile; a
disagreeing body value is logged and ignored.

**This is the first case where one of US-237's FOR ALL USING(true) policies has
been shown to be load-bearing.** The handler fix stands on its own, but fixing
that policy (scoping it TO service_role) is what would give defence in depth.

### Two hardenings
- api-management minted API keys with unvalidated `permissions` and stored
  `rate_limit_per_hour` verbatim — and api-auth enforces that column as the
  per-key ceiling, so a company admin could mint a key with no practical limit.
  An unknown grant string also matched nothing, so a typo silently produced a
  key weaker than its owner believed. Grants are checked against the known set
  (projects:read/write, estimates:read, invoices:read) and the rate is clamped.
- manage-alert-rules and manage-schedules spread the body into their update
  paths while their create paths listed columns explicitly. root_admin-only, so
  hygiene rather than a hole, but the two paths disagreeing is how holes start.

### Seven reviewed and left alone
Each recorded in the guard with the specific reason, not a blanket "reviewed":
change-subscription writes subscription_tier only after Stripe was updated with
the real price; blog-social-integration, quickbooks-callback and
quickbooks-disconnect all write company_id into tables whose `FOR ALL USING`
policy Postgres also applies as WITH CHECK, so a foreign id matches nothing.

### A false positive worth remembering
store-stripe-keys looked like IDOR to the filter-based sweep — a service-role
update filtered by a body-supplied company_id. Its ownership check is imperative
(compare `userProfile.company_id` to the body value, throw on mismatch) rather
than a `.eq()` in the query chain, so a sweep that only reads query chains
cannot see it. Any future taint tool here needs to account for guard-then-query,
not just query-shape.

### The guard
scripts/check-edge-privilege-writes.mjs, in the pre-commit hook and CI. Fails on
any body spread into insert/update/upsert, and on any privilege/tenancy column
set from request input that is not in REVIEWED with a reason. It also reports
REVIEWED entries that no longer match anything, so the list cannot rot.

Note it is deliberately strict about spreads: `...(cond && { k: v })` trips it
even though that idiom is safe. Use pickAllowed() from _shared/writable-columns.ts
rather than teaching the guard to recognise conditional spreads — one obvious
way to write it is worth more than a cleverer checker.

2026-08-27 — US-237 follow-up: the scoped tables had no user-JWT write path
================================================================================

### First, a correction to yesterday's US-297 write-up
I recorded that usage_metrics' `FOR ALL USING (true)` policy meant RLS was not
scoping track-usage's write, making it a live cross-tenant hole. That was too
strong. US-237's migration 20260712120000 scopes exactly that policy to
service_role. Whether the permissive version is still live in production is not
knowable from this repo — there is no DB access here and US-248 (an auditable
migration-to-prod pipeline) is still open. The cross-tenant write was possible
only if that migration has not been applied. The handler fix stands either way,
since it should never have trusted the body.

Chasing that down turned up something worse.

### The finding: the "verified safe" analysis only checked the frontend
20260712120000's header says the 12 tables it scopes are safe because the
frontend either does not touch them or only reads them through a separate
company-scoped SELECT policy. True of the frontend. Nobody checked the edge
functions that build their client from `initializeAuthContext()` — which is a
user-JWT client, not a service-role one.

Three of them write scoped tables that way:

  track-usage         usage_metrics               insert + update
  usage-billing       usage_metrics               insert + update
  workflow-execution  workflow_step_executions    insert x2

Those tables end up with a company-scoped SELECT policy and nothing else, so
after the migration a user-JWT client has **no write policy at all**.

And every one of those six call sites discarded the error — `await supabase
.from(...).update(...)` with nothing destructured, or `const { data } = ...`
without `error`. Supabase returns errors rather than throwing, so the handler
carries on and returns `{ success: true }`. The failure mode is silent: usage
simply stops being billed, workflow step history simply stops being recorded.

So either 20260712120000 is not applied in production, or those three have been
quietly failing since it was. Nothing in the repo distinguishes the two.

### The fix
All three authorise the caller in the handler — company_id from the caller's own
profile, and workflow-execution fetches the workflow RLS-scoped first so a
cross-company id never reaches the write — then write with
`createServiceClient()` from _shared/service-client.ts. The helper carries the
rule in its doc comment: service role means RLS is off for that query, so the
handler owns authorisation. The discarded errors are surfaced.

### The guard
scripts/check-rls-write-paths.mjs fails when any of the 12 scoped tables is
written with anything but a service-role client. In pre-commit and CI.

**If more tables get scoped later, add them to SERVICE_ROLE_ONLY in that script
and run it before shipping the migration.** That check is precisely what the
original "verified safe" pass was missing, and it is cheap.

### The general lesson
"The frontend doesn't write this table" is not the same as "nothing with a user
JWT writes this table." Edge functions using initializeAuthContext() are user-JWT
clients and are subject to exactly the same policies as the browser. Worth
remembering for the 4 tables US-237 deferred (workflow_executions,
workflow_analytics, calendar_events, webhook_events) — check the edge functions
before scoping those too.

Set out to check the four tables US-237 deferred. Ended up rewriting the guard

### Blind spot 1 — shorthand properties
check-edge-privilege-writes.mjs matched `company_id: someBodyVar` as a

    .insert({ company_id, title, ... })

was invisible. That is exactly how sync-calendar wrote a body-supplied

destructures from a *variable* that is tainted, not from the call. The trail
died one hop in. Ten more sites appeared once that was fixed.

one, a destructure of an already-tainted variable, a plain alias, a cast, and a
property read. Each form carries a comment naming the finding it hid, so nobody
"simplifies" one away.

**Lesson: a guard that reports zero is not evidence until you have tried to make
it lie.** I marked US-297 done on a clean run of a checker with two holes in it.

  client, companyId straight from the body. verify_jwt is on, so the caller is
  authenticated — but authentication is not authorisation. Any authenticated
  user could drive CRM automation for any company: enrol their contacts in
  campaigns, queue email against them, write crm_activities rows.
- **blog_social_webhook** — same shape. It already fetches the blog post, which
  carries the authoritative company_id, so that is what it uses now.
- **sync-calendar** — body company_id upserted into calendar_events, one of the
  four still carrying FOR ALL USING (true), so RLS was not scoping it.

### The four deferred tables: restrictive policies, not scoping
The migration header said these were deferred because the frontend writes them
directly. Checking: only workflow_executions actually has a frontend write
(WorkflowExecutionService.cancelExecution). The other three are read-only from
src/, and iOS touches none of the four.

Scoping the permissive policies would still be a tightening — it removes the
only write path those flows have — which CLAUDE.md rules out in one release.
So 20260827023111 adds **RESTRICTIVE** policies instead. Restrictive policies
are AND'd with the permissive ones rather than OR'd, which means:

  * a same-company write still passes, so nothing legitimate breaks and there
    is no mixed-client window to wait out;
  * a cross-company write is denied whatever the permissive policy says;
  * granted TO authenticated, anon only, so service_role is unaffected whether
    or not it carries BYPASSRLS on a given deployment;
  * root_admin keeps cross-company access, matching each table's SELECT policy.

This is a better tool than I had been reaching for. Where the goal is "remove
access nobody legitimately has" rather than "change what legitimate clients may
do", a restrictive policy does it in one release with no rollout window.

### A live hole it closes
WorkflowExecutionService.cancelExecution filters only by execution id:

    .from('workflow_executions').update({ status: 'cancelled' })
    .eq('id', executionId).eq('status', 'running')

With FOR ALL USING (true) OR'd in, any authenticated user could cancel any
company's running workflow. Client-side scoping would have been cosmetic — an
attacker calls PostgREST directly — so the fix belongs in the policy, and that
is where it went.

### If the deferred four are ever scoped
Add them to SERVICE_ROLE_ONLY in scripts/check-rls-write-paths.mjs first and run
it: workflow-execution and sync-calendar write them with a user-JWT client
today. That note is in the script itself.

2026-08-27 — US-237: the SSO pending-state tables were public
================================================================================

### The find
saml_pending_requests and oauth_pending_states were created like this:

    CREATE POLICY "Service role manages OAuth states"
      ON oauth_pending_states FOR ALL
      USING (true)
      WITH CHECK (true);

The name says service role. There is no TO clause, so the policy is granted to
PUBLIC — on a Supabase project that means anon and authenticated, both reachable
with the publishable key that ships in the web bundle.

oauth_pending_states stores `state` and, for PKCE flows, `code_verifier`. The
verifier is the secret that binds an authorization code to the client that
started the flow; sso-oauth-callback reads it back and sends it with the token
exchange:

    if (storedState.code_verifier) {
      tokenParams.set("code_verifier", storedState.code_verifier);

So SELECT access defeats PKCE for any authorization code an attacker observes.
Read access to `state` defeats the CSRF check. Write access lets them seed a row
with a return_url of their choosing.

**A policy whose name says one thing and whose grant says another is the worst
kind, because every reader after the author assumes the name is true.** US-237's
own deferral note called these "auth-flow data" whose public reads might be load
bearing — reasoning from the name rather than the grant.

They are not load bearing: nothing under src/, Brikly-iOS/ or mobile-app/
references either table, and all three functions that do (sso-oauth-init,
sso-saml-init, sso-oauth-callback) build a SERVICE_ROLE_KEY client. So scoping
to service_role is a tightening with nothing on the other side of it.
Migration 20260827030000. Both tables added to check-rls-write-paths.mjs.

### feature_announcements
Restrictive company scope (20260827031000). Its publish path is

    .update({ status: 'published', ... }).eq('id', id)

filtered only by id, so with FOR ALL USING (true) OR'd in, any authenticated

### seo_meta_tags — deliberately NOT fixed, and why that matters
It has the same exposure: any authenticated user can rewrite any site's SEO
metadata. The obvious fix is a restrictive site_id scope. I wrote it, then threw
it away.

Its two writers — src/utils/seoBackendSync.ts (upsert) and

**A restrictive WITH CHECK denies a row whose tenancy column is NULL**, because
`NULL = x` evaluates to NULL, not true. If site_id lands NULL, that policy stops
SEO management working entirely. Shipping it would have been the same mistake

verified fact. Filed as US-298 instead.

### The pattern, now that it has been used four times
- Table has a tenancy column AND legitimate same-tenant client writes
  → `AS RESTRICTIVE ... TO authenticated, anon`. AND'd rather than OR'd, so
  same-tenant writes keep working, cross-tenant is denied, and there is no

  tightening RLS, because it removes only access nobody legitimately had.
- No client touches the table at all
  → scope the permissive policy to service_role. Simpler, equally safe.
- Either way: check what the writers actually send first. NULL tenancy is the

2026-08-27 — the silent-write class, and the offline data loss it was causing
================================================================================

Chased the discarded-error pattern I flagged last tick. It is worse than a code
smell: it has now cost something three separate times, and one of those is
active data loss affecting real users.

### The bug — OfflineDataManager destroyed queued field data
    await supabase.from('time_entries').insert(pendingTimeEntries);
    localStorage.removeItem('pending_time_entries');
    synced += pendingTimeEntries.length;

**supabase-js returns errors rather than throwing them.** So the surrounding
try/catch never fired, the removeItem ran unconditionally, the counter went up,
and the user got a "Sync Complete" toast. An RLS denial, a constraint violation
or a validation failure permanently destroyed the field worker's queued time
entries, expenses, quality inspections and tasks.

Time entries are payroll. This is the most consequential thing found in this
session — worse than any of the security findings, because it is silent, active
and affects the exact workflow the mobile app exists for.

Each queue now clears only after its insert returns without an error, keeps its
rows for the next attempt otherwise, and the toast names what did not save.
`pendingUploads` reflects what is still queued instead of resetting to zero.

`pending_locations` was worse still: no destination table at all. The code
cleared the queue under a "Mock sync - in production would sync to actual table"
comment, so queued locations were thrown away on every single sync. Now kept and
logged.

### The subtlety that makes this hard to find
`catch {}` is usually **not** what hides these. supabase-js resolves rather than
rejects, so the error never reaches a catch — it sits unread in the returned
object. Grepping for empty catch blocks finds the wrong thing. The guard checks
the destructuring instead: a write whose result is discarded, or destructured
without `error`.

### The dangerous shape, specifically
A write followed by an **irreversible local action**: clearing a queue, marking
something synced, incrementing a counter, showing a success toast. That is what
turns a failed write from a no-op into data loss. A write whose failure just
means "nothing happened" is a bug; a write whose failure means "and now the only
copy is gone" is an incident.

### Scale, and the guard
330 writes across the repo discard their error — 258 in edge functions, 72 in
the web app. scripts/check-silent-writes.mjs is the ratchet: pre-commit and CI,
shrink-only. Filed as US-300, to be triaged by consequence (money, payroll,
compliance evidence, identity) rather than swept alphabetically.

Deliberately ignoring an error is a legitimate outcome — destructure it and say
why in a comment, so the next reader knows it was a decision.

### Prior appearances of the same pattern
- track-usage / usage-billing / workflow-execution wrote to tables their client
  had no RLS write path for, and reported success (US-237 follow-up).
- useSecurityMonitor has never recorded a single security event (US-299).

### stripe-webhook had working retry machinery it never reached
This is the one worth understanding. The webhook already does the right thing on
failure: a handler that throws gets its attempt recorded against webhook_events
and returns 500, and a non-2xx is what makes Stripe retry the event.

But every handler discarded the error from its database write. So a failed
subscriber update, refund update or dispute insert fell straight through to
`return new Response(JSON.stringify({ received: true }), { status: 200 })`.
Stripe marked the event delivered and never sent it again. The divergence
between Stripe and the database became permanent, silently.

The fix was not to build retry handling — it was already there, correct and
unused. Nine writes now throw.

**Worth generalising: before adding error handling, check whether the codebase
already has some that nothing is reaching.**

### throw vs log — the judgement, not the mechanism
Wrapping a write with an error check is mechanical and scripted. Deciding what
to do with the error is not, and the split that matters is what the caller has
been told:

- **throw** where a success response depends on the write. calculate-proration,
  process-refund, handle-chargeback, billing-automation, usage-billing, and
  manage-complimentary-subscription — that last one told an admin "Complimentary
  subscription granted" whether or not the subscriber row actually changed.
- **log** where it is a background sync and failing the request helps nobody.
  check-subscription, create-stripe-checkout, setup-payment-method,
  trial-management, convert-trial-to-paid, failed-payment-recovery,
  process-dunning, send-renewal-notification, quickbooks-sync. Turning a
  transient Stripe hiccup into a broken checkout would be its own bug.

### Verifying a scripted transform
The transform is AST-driven: find a write whose result is discarded, bind
`const { error: <op><Table>Error }`, add the check. The failure mode it can
introduce is two writes to the same table in the same scope producing a
duplicate const.

esbuild catches exactly that ("The symbol X has already been declared") — I
confirmed it does with a deliberate two-line test file before relying on it,
rather than assuming. A regex-based scope check flagged five files; all five
were false positives, because const is block-scoped and the duplicates sat in
sibling branches. **Confirm your checker catches the thing before you trust it
reporting nothing** — same lesson as the privilege-write guard's blind spots.

2026-08-27 — US-202: 'unsafe-inline' is gone, and the blocker was not the scripts
================================================================================

### What actually blocked it
The story frames this as hash-pinning four inline scripts. That part was easy.
The thing that would have broken production was one **inline event handler**:

    <link rel="stylesheet" href="/fonts/inter.css" media="print" onload="this.media='all'">

Hashes cover inline `<script>` bodies. They do **not** cover event handlers.
Remove `'unsafe-inline'` and that onload never fires, the sheet stays at
`media="print"`, and fonts silently never apply. No console error a developer
would notice on a normal page load, no test failure.

The sheet is 545 bytes, same-origin, and the critical weight is already
preloaded on the line above — so the async trick was buying almost nothing. It
now loads plainly, which also removes the `<noscript>` duplicate.

**Checking for inline handlers is the step to do first** when removing
'unsafe-inline', before computing a single hash.

### Verified before trusting: does the build rewrite inline scripts?
If Vite minified or touched inline script bodies, hashing `index.html` would
produce digests that never match what the browser sees. It does not — source and
`dist/index.html` produce identical sha256 digests for all four. Re-checked
against the built output after making the change, not just before.

### The guard is the deliverable, not the hashes
The failure mode here is silent in production and invisible to build and tests:
edit an inline script by one character and its hash no longer matches, so the
browser refuses to run it. One of the four is the Trusted Types bootstrap, which
cannot be externalized because it has to run before app scripts.

scripts/check-csp-hashes.mjs recomputes from index.html and fails on:
a missing hash, an orphaned hash left by a deleted script, 'unsafe-inline' or
'unsafe-eval' returning, a new inline event handler, or Trusted Types being
dropped. Mutation-checked all five before wiring it in.

### A landmine found on the way — US-301
`src/utils/security.ts` has `addSecurityHeaders()`, which injects a **second**
CSP via meta tag. Its production script-src is
`'self' https://api.ipify.org https://*.posthog.com` — no Stripe, no GTM, no
Sentry, no Google or Apple sign-in, no inline hashes. CSP policies combine
restrictively, so if that ever ran alongside the header, a resource would have
to satisfy both: checkout, analytics, SSO and the Trusted Types bootstrap would
all break.

It does not run. It is called only from `useSecurityEnhancement`, and that hook
is mounted nowhere. So it is a landmine, not an outage — a plausible-looking
security hook that breaks payments the day someone adds it to a layout because
the name sounds right.

That is now three of the same shape this session: US-296 (unreferenced MFA stubs
minting fake backup codes), US-299 (a security hook that has never recorded
anything), and this. **Unmounted, security-named code is its own risk category**
— it reads as protection, so nobody audits it, and it gets wired up by someone
trusting the name.

### Left for a human
AC5: exercise OAuth/SSO and Stripe redirects in a real browser under the new
policy. Their origins were already explicitly allowlisted and none relied on
'unsafe-inline', so no breakage is expected — but expected is not verified.

One trap for any follow-up: **do not add 'strict-dynamic'.** It makes the host
allowlist be ignored, which would break GTM, Stripe and Google sign-in.

2026-08-27 — sweeping for unmounted security code, and what it turned up
================================================================================

Three times this session I found code that looks like a security control, is not
wired up, and would do harm if it were: US-296 (MFA stubs minting Math.random()
backup codes), US-299 (a hook whose audit inserts RLS has always rejected),
US-301 (a dead second CSP that would break checkout). So I swept for the shape
rather than waiting to trip over the fourth.

### The question that makes the sweep useful
Not "is this dead code" — that is a tidiness question and there are 295 candidate
modules, most of them boring. The useful question is **"what happens if someone
adopts it?"** Dead security code is adopted on the strength of its name, by
someone who assumes a file called ProtectedRoute protects routes.

### Two route guards, and the dead one failed open
- `src/components/ProtectedRoute.tsx` — live, exports RouteGuard, wired up in
  routes/appRoutes.tsx, fails closed, has a redirect circuit-breaker.
- `src/components/auth/ProtectedRoute.tsx` — imported nowhere. Both role checks:

      if (role && !allowedRoles.includes(role))

  which **skips the comparison entirely when role is null or undefined**. A
  signed-in user whose profile had not loaded passed every role gate.
  RequirePermission had the same shape.

Nothing is exposed today, because the live guard is the one in use. But the dead
one lives under `auth/`, which reads as the more canonical of the two paths, and
its Outlet-based API is the shape react-router's own docs encourage — so it is
exactly what a new contributor reaches for.

Both now fail closed, with tests. Mutation-checked: restoring the old condition
fails 3 of 8 assertions.

### An always-allow rate limiter
`SecurityService.checkRateLimit` returned `{ allowed: true, remainingAttempts: 5 }`
unconditionally, and its catch also returned `{ allowed: true }`. A caller asking
"may this proceed?" always got yes. It now throws, so anyone wiring it up finds
out in development rather than shipping a control that does nothing. Real rate
limiting is server-side in `_shared/rate-limiter.ts` — the only place it can be
trusted, since a browser-side limiter is controlled by the caller.

### On the 295 number
Do not quote it. The detector counts named imports and JSX tags; it does not
follow `React.lazy(() => import(...))` or dynamic `import()` specifiers, so an
unknown share are false positives — `AuthCallback` and the live `ProtectedRoute`
both showed up initially. What is trustworthy is the ~26 security-named entries,
because those were checked individually. Fixing the detector before quoting the
count is in US-302.

### Why fixed in place rather than deleted
The sandbox classifier blocks file deletion, as it did for the MFA stubs in
US-296. So the hazards are neutralised where they sit — fail-closed logic, a
throwing stub, a comment pointing at the live equivalent. Deleting remains the
right end state and is US-302's first AC.

2026-08-27 — US-243: ceilings on the calls that cost money
================================================================================

14 functions now enforce a per-caller rate limit. The limiter had existed in
_shared/rate-limiter.ts the whole time; the gap was that the expensive functions
never called it.

### Key on the user, never on the request body
An IP ceiling is shared by everyone behind one customer's NAT, and a stolen
token steps around it by changing address. So the identifier is the caller's
user id wherever there is one.

`process-voice-command` is the cautionary case. It takes `user_id` in its
**request body** — which is exactly what must not be used as a limit key, since
a caller can rotate a body field and never hit the ceiling. It and voice-to-text
now resolve the user from the JWT (verify_jwt is on for both) and fall back to
IP only where there is no user, so a service-key path keeps working.

Before signup there is no user at all, so signup-with-otp keys on IP because
that is the only handle that exists.

### The email side was worse than the AI side
- **signup-with-otp had no throttle of any kind.** Unauthenticated, sends mail,
  no ceiling. That is an open relay for bombing someone's inbox or burning SES
  quota and reputation.
- **reset-password-otp had a per-email throttle but no per-IP one.** So one
  source could spray across many addresses and never trip it — the per-email
  check cannot see that pattern.

**Those are two different controls and both are wanted:** per-email stops one
address being targeted, per-IP stops one source spraying. send-auth-otp already
had both, and is the model the others now follow.

Cron-driven senders (send-payment-reminder, send-scheduled-emails,
send-usage-alert) are deliberately left alone — a ceiling there throttles
scheduled work, not an abuser.

### A trade to know rather than discover
`checkRateLimit` returns **allowed** when it cannot reach the database. That is
the right default for a cost control — failing open beats taking the product
down — but it means a database outage removes the ceiling entirely. Now
documented on the helper, along with the point that these calls want
provider-side spend caps (OpenAI, SES) as the real backstop. A limiter the
attacker can disable by causing load is not a spend guarantee.

### Envelope
rateLimitResponse now emits `success: false` and `timestamp` alongside the
existing error/retryAfter/limit/requestCount — additive, so a client reading the
old fields is unaffected. The Retry-After and X-RateLimit-* headers are
unchanged, and those are what a client should actually key on.

2026-08-27 — US-252: the QuickBooks sync was importing a prefix of the data
================================================================================

### The bug
    `SELECT * FROM ${entityType}` — no STARTPOSITION, no MAXRESULTS

QuickBooks answers that with **at most 1000 rows and no indication that more
exist**. So a company with 4000 customers imported 1000 of them, and the result
was indistinguishable from a company that has 1000 customers. No error, no
warning, a "completed" sync log.

It also had no throttle handling. A 429 threw, the caller's try/catch logged
`Error syncing customers` and moved on to the next entity — so a throttled run
dropped a whole entity for that sync.

Now pages in windows of 500 until a page comes back shorter than the window.
That short page is the only end signal available: the QuickBooks query API has no
next-page cursor.

### Retry choices worth keeping
429, 503 and 500 retry up to four times, honouring `Retry-After` when Intuit
sends it and backing off exponentially otherwise. **401 is deliberately not
retried** — a bad token does not fix itself, and retrying only delays the
reconnect prompt the user actually needs to see. Retrying everything is a common
reflex and it is wrong here.

### Making truncation visible
`records_processed` alone cannot show truncation, because it counts what we
wrote and we wrote everything we were given. The log now also carries
`records_fetched`, which separates two different failures:

  equal          -> everything QuickBooks returned was written
  fetched > processed -> rows were dropped on our side, in syncCustomer/syncItem/...

plus `truncated_entities` (paging hit its ceiling without a short page) and
`throttle_retries` (early warning that a company is outgrowing its sync window).

### A hazard caught before shipping
Those three columns did not exist. The sync-log update discards its error — one
of the 272 sites in US-300 — so naming a column PostgREST rejects would have made
the **entire log write fail silently** while the sync reported success. I checked
the generated types before committing and added migration 20260827050000
(nullable, no backfill, additive per CLAUDE.md).

**Worth generalising: any write naming a new column needs the schema checked
first, because wherever the error is unread the failure is invisible.** The
silent-write backlog and the schema-drift backlog compound each other.

### Structural rule for edge functions
The paging moved to `_shared/quickbooks-paging.ts` with an injectable `fetchImpl`
and `sleep`. `quickbooks-sync/index.ts` imports Deno URL modules, which vitest
cannot load — so **logic that needs testing has to live in `_shared/`** until
Deno is available in CI. Nine tests, mutation-checked three ways: reverting to a
single unpaged request fails 2, dropping the throttle retry fails 4, ignoring
Retry-After fails 1.

2026-08-27 — US-251: edge functions can now report their own failures
================================================================================

193 functions reported failures with console.error and nothing aggregated them.
A billing webhook that starts failing at 3am paged nobody.

### No SDK, on purpose
Sentry has a documented HTTP envelope endpoint, so `_shared/observability.ts`
posts to it with plain fetch. Three reasons, in order of weight:

1. **It can be tested.** Edge-function entry points import Deno URL modules that
   vitest cannot load. A module with zero imports lives in `_shared/` and gets
   16 real tests. An SDK-based one would have got none.
2. A URL import costs cold-start time on every invocation of every function.
3. The envelope format is stable and documented; the risk of hand-rolling it is
   low and the surface is about 40 lines.

The URL-import block in this sandbox pushed me to look at the envelope API, but
the testability argument is why it stayed.

### Scrub on shape, not just on key name
The obvious approach is a list of sensitive field names. That misses the case
that actually matters: **a secret inside an error message.** `Error: auth failed
for sk_live_ABC...` has no field name to match on.

So scrubbing runs over the whole serialized event and matches both — keys by
name at any depth, and secret-shaped values anywhere: JWTs, sk_live/sk_test,
whsec_, bearer tokens, email addresses. Emails are in there because they are PII
and error messages are full of them.

### Never throws, never rejects
On a bad DSN, a dead network, or a 429 from Sentry. Reporting an error must not
be able to cause one — the same rule the audit writer follows (US-244). Both
mutation-checked: letting a transport failure escape fails a test.

### Where it is wired
stripe-webhook, quickbooks-sync, process-dunning, process-funnel-queue. The last
two are cron-driven, which is the case that most needs this: nobody reads the
response, so a stalled queue looks exactly like an idle one.

### Left for you
Set `EDGE_SENTRY_DSN` as a **Supabase secret**, not a build variable — it is read
at runtime via Deno.env and must not reach the web bundle. Documented in
env.example. Until it is set, captureException is a no-op; handlers still log to
the platform's own logs, they just do not aggregate or alert. Then throw
deliberately in one function and confirm the event lands (AC4).

2026-08-27 — US-212: the error backlog contains real bugs, not just noise
================================================================================

1854 TypeScript errors is easy to treat as one undifferentiated pile of type
noise to be suppressed. Mining the *small* classes instead of the big ones found
five calls that have never executed.

### PostgrestBuilder has then() but not catch()
    await supabase.rpc('increment_lead_score', { ... }).catch(() => {});

`PostgrestBuilder implements PromiseLike` — `then()` and nothing else. So
`.catch` is undefined, calling it throws a TypeError, and it throws **before the
request is sent**, because the builder only issues its request when `then()` is
called.

Five such calls, none of which has ever reached the database:

  increment_line_item_use_count   LineItemLibraryBrowser
  increment_session_calculations  calculatorAnalytics
  increment_lead_score x3         calculatorAnalytics

`increment_line_item_use_count` is defined in the migrations, so that is a
working feature the `.catch` was silently preventing.

### A distinction worth not flattening
A sixth site chained `.then().catch()`. That one **worked at runtime** — `then()`
returns a real Promise — it just could not typecheck, because `then()` is
declared as returning `PromiseLike`. Same error code, completely different
consequence. Reporting both as "five bugs" would have been wrong.

### What it exposed — US-303
`increment_lead_score` and `increment_session_calculations` are not defined in
any migration. Their "Silently handle if lead scoring not available" comments
were honest about the risk. Now the calls are actually attempted and log when the
RPC is missing, which is how this surfaced at all.

Checked against the migration SQL rather than the generated types, because
types.ts is stale (US-263) and its absence would prove nothing. Note they could
still exist in the live database if someone created them by hand — which is
precisely what US-248 exists to stop.

### The lesson for the rest of US-212
Do not assume the backlog is noise. TS2551 ("did you mean...?") is 16 errors and
contained a live bug class. TS2554 (wrong argument count) and TS2532 (possibly
undefined) are worth the same treatment before anyone reaches for a bulk
suppression. The big classes — TS2345/2322/2339, about 1367 of the 1847 — really
are mostly Supabase type drift and want US-263 first.

## US-304 — the XSS test suite was testing nothing

A single failing test after d8fae33: `useSanitizedForm > XSS Prevention >
prevents script injection in HTML fields`, asserting the output does not contain
`<script>`. It did contain `<script>`. I had not touched `useSanitizedForm.ts`
in fifteen commits, so the reflex answer was "pre-existing, not mine". That was
true and completely beside the point.

### The lead was already in the file
`stripHtml` in `src/lib/security/sanitize.ts` carries this:

    // Safety net: in some environments DOMPurify with an empty allowlist
    // still leaves inline tags in the output. Strip any that remain.

Someone hit this before, wrote a regex post-pass for `stripHtml`, and stopped.
`sanitizeHtml` — the one that has to keep tags, so a regex cannot rescue it —
was left with the bug.

### Root cause, reproduced in six lines
happy-dom does not implement the DOM spec's NodeIterator pre-removing steps.
Remove the node the iterator is sitting on and iteration ends, instead of the
reference moving to the next node.

    doc.body.innerHTML = '<i>1</i><i>2</i><i>3</i><i>4</i>';
    const it = doc.createNodeIterator(doc.body, NodeFilter.SHOW_ELEMENT);
    while ((n = it.nextNode())) { visit(n); if (n.textContent === '2') n.remove(); }

    happy-dom  visited: BODY I1 I2
    jsdom      visited: BODY I1 I2 I3 I4

DOMPurify sanitizes by walking the tree with `createNodeIterator` and removing
as it goes. So under happy-dom it stops sanitizing at the first node it strips:

    'Hello<script>evil()</script><b>W</b>'
      happy-dom => '<script>evil()</script><b>W</b>'
      jsdom     => 'Hello<b>W</b>'

Note which half survived. The payload stayed; the innocent text was dropped.

### What that cost
Six test files, 616 assertions, across `xssPayloads`, `securityRegression`,
`trustedTypes` and both `sanitize` suites. None of them were testing the
sanitizer. Some passed anyway — whether a given assertion held depended on
where in the payload the first removal happened to land, which is why exactly
one test was red and the rest looked fine. And US-213 has just made `Unit Tests`
a required merge check, so that one red test would have blocked every merge.

### The fix, and two things I deliberately did not do
Per-file `@vitest-environment jsdom` on the six files, plus
`scripts/check-sanitizer-test-env.mjs`, which computes the DOMPurify taint set
as a fixpoint over the `src/` import graph and requires the docblock on any test
that reaches it. The taint analysis found three files my hand-picked list had
missed, and one exemption I could justify in writing (`sqlInjection.test.ts` —
`sanitizeSqlInput` is three string replaces and never touches the DOM). It found
one file I had wrongly added the docblock to, which I removed.

**Not** switching the suite default to jsdom. A full-suite jsdom run was still
going at 30 minutes against roughly 4 under happy-dom; the six files that need
it finish in 4.3s. The guard prints an explanatory message and exits 0 if the
default is ever switched, so it cannot outlive its reason.

**Not** adding a regex element-allowlist post-pass to `sanitizeHtml`. A regex
post-pass is exactly what let this sit undiagnosed for however long — it made
`stripHtml` look fixed. The sanitizer is correct against a spec-compliant DOM;
the environment was wrong, so fix the environment.

### Mutation-tested, as usual
Stripped the docblock from each of the six in turn: caught six of six. Then
`vitest run` on the six under jsdom: 616 passed, 4.28s, including the test that
started this.

### Left open
`src/lib/validations` exports a *second* function named `sanitizeHtml`, regex
based, which strips everything between `<` and `>` — its own test asserts
`sanitizeHtml('1 < 2 > 0') === '1  0'`. Two exported functions with the same
name and different semantics, one of which quietly mangles arithmetic. Not in
scope here; worth a story.

## US-305 — the RPC that let anyone overwrite anyone's document

I was checking one thing: does `document_versions.file_path` hold a raw storage
path, so the US-289 company-documents policy can join on it rather than pattern
match? It does. But reading the function that writes it turned up this.

`public.create_document_version(p_document_id, p_file_path, p_file_size,
p_checksum, p_version_notes)` is `SECURITY DEFINER` with `search_path = ''`. It
runs past RLS on both `documents` and `document_versions`, and it carried no
authorisation check of its own. Its last statement:

    UPDATE public.documents
    SET file_path = p_file_path, file_size = ..., version = ..., updated_at = now()
    WHERE id = p_document_id;

Any authenticated user, of any company, could pass any document id and repoint
that document at a file of their choosing. `file_path` is what every reader
downloads. The victim's document keeps its name, its category, its version
history — and serves the attacker's file. The only trace is an `updated_at`
bump.

### The fix, and the trap I already fell into once
`20260827070000` CREATE OR REPLACEs the function rather than editing the merged
`20250801021602`. The guard denies only the genuine cross-tenant case:

    d.id = p_document_id
    AND d.company_id IS NOT NULL
    AND d.company_id IS DISTINCT FROM public.get_user_company(auth.uid())
    AND public.get_user_role(auth.uid()) IS DISTINCT FROM 'root_admin'

`IS NOT NULL` is load-bearing. `DocumentManagement` writes
`company_id: userProfile?.company_id`, which can persist NULL, and a guard that
denied those would strand versioning on historical rows with nothing the user
could do about it. That is exactly the NULL-tenancy trap that made me drop
`seo_meta_tags` from the restrictive-RLS work earlier in this session — same
shape, caught this time before shipping it.

Signature, parameter names, defaults and return type unchanged, so PostgREST
still resolves calls from every client already in the wild. Per CLAUDE.md a
tightening is normally a multi-release change; this ships in one because the
only calls whose behaviour changes are cross-tenant writes no legitimate client
makes.

### Two overloads
`create_document_version` exists twice: `(uuid, jsonb)` from `20250126230001`,
and this `(uuid, text, integer, text, text)` from `20250801021602`. PostgREST
resolves by named arguments, so the app's five-key call reaches the one I fixed.
The two-arg overload is unreferenced and still unscoped. Dropping a function is
destructive, so it needs its own release — recorded on the story rather than
done here.

### Also landed
`20260827060000_company_documents_read_policies.sql`: the supplementary SELECT

`document_versions.file_path` to `documents.company_id`. Modelled on

`securityDefinerScoping.test.ts` pins both. It resolves the function against the

## US-306 — the audit trail was a guestbook

US-299 says, in its own words, that `audit_logs` "has only SELECT policies —
there is no INSERT policy for authenticated or anon — so every one of those
inserts is rejected by RLS." I opened the migrations to confirm it before
deciding how to fix the hook. It is not true, and the truth is worse.

    "System can insert audit logs"   20250703164308   FOR INSERT WITH CHECK (true)
    "site_audit_logs_insert"         20251203000002   FOR INSERT WITH CHECK (true)

Neither carries a `TO` clause, so both grant PUBLIC. The second dropped the
SELECT policies it replaced and left this one standing. Permissive policies OR
together, so `authenticated` and `anon` could both insert whatever they liked —
and every column an investigator would trust is caller-supplied: `user_id`,
`company_id`, `action_type`, `risk_level`, `description`, `created_at`.

Fabricate entries against another user. Plant them in another company's trail.
Bury a real event under ten thousand rows of noise. CLAUDE.md makes logging
critical actions to the trail non-negotiable, which is precisely what makes a
forgeable trail load-bearing rather than academic.

This is the third time this session the same shape has turned up: a policy
*named* "System can …" with no `TO` clause, which reads as service-only and
grants PUBLIC. `oauth_pending_states` was the first. The naming is doing the
work the SQL isn't. Worth sweeping the rest of that pattern.

### The fix
`20260827080000`: RESTRICTIVE `FOR ALL TO authenticated, anon`, `USING (true)`
so reads stay with the existing SELECT policies, `WITH CHECK (false)` so no
client write passes. Restrictive because the permissive policies are merged and
cannot be edited, and because restrictive policies are AND'd — no window where a
legitimate writer loses its path. `FOR ALL` rather than `FOR INSERT` so a later
UPDATE or DELETE policy without a `TO` clause can't reopen it from the other
side.

Nothing legitimate loses a write. Edge writers build SERVICE_ROLE_KEY clients;
the in-database writers are SECURITY DEFINER functions and the BEFORE INSERT
trigger from `20250202000012`, which run as the table owner; and the only
browser-side writer is `useSecurityMonitor`, mounted nowhere.

### My own guard was wrong about it
`check-rls-policies.mjs` failed the migration — it matched `FOR ALL … USING
(true)` without noticing `AS RESTRICTIVE`. A restrictive `USING (true)` is a
no-op for reads; the deny lives in its `WITH CHECK`. Left alone, the guard would
have pushed the next author towards deleting the very policies that close these
holes. Fixed, and mutation-tested both directions: a permissive probe is still
caught, the restrictive one is skipped.

### What it does to US-299
That story's whole premise inverts. The browser inserts were succeeding, not
being rejected. What survives is that `useSecurityMonitor` is imported only by
its own test, so nothing has ever reached the trail from a browser anyway — and
the rows it builds carry no `company_id`, which is its own tell. With US-306 in
place the hook cannot be wired up as written.

### The rest of the class — 68 open policies
`audit_logs` was not one bad policy, it was one instance. Scanning the
migration history for permissive policies with `WITH CHECK (true)` or a
non-`FOR ALL` `USING (true)`, no `TO` clause, and not `AS RESTRICTIVE`, turns up

## US-307 — no rate limit had ever blocked a request

I only went looking because `rate_limit_violations` was in my first draft of the
US-306 deny list and I wanted to know who wrote it. The answer: the only writer
is unreachable.

    requestCount = violations.length      // rows in rate_limit_violations
    allowed = requestCount < maxRequests  // 0 < 3 → true
    if (!allowed) insert a violation row  // never runs

From an empty table the count is 0, so every request passes, so no row is
written, so the count stays 0. It cannot bootstrap. `dos-protection`'s three
references to that table are all selects. `enforceRateLimit`, which I added
earlier in this session, delegates straight to `checkRateLimit` and inherits it.

So all 14 functions `check-rate-limit-coverage.mjs` reports as enforcing a limit
were calling a function that always returns `allowed: true` — `signup-with-otp`,
`send-auth-otp`, `verify-auth-otp`, `verify-mfa-login`, and the AI endpoints
that spend money per call.

### Why nobody caught it
`src/lib/__tests__/rateLimiter.test.ts` **re-implemented** the limiter rather
than importing it, and handed the copy a mock pre-seeded with violation rows. It
proved the arithmetic and never asked how a row gets into the table. Twenty-odd
green cases, and not one of them could have found this.

A test that reconstructs its subject tests the reconstruction. That is the part
worth carrying forward.

### Proof before fix
`supabase/functions/_shared/rate-limiter.test.ts` drives the real module from an
empty store: 50 requests against a limit of 3, zero blocked, zero rows written,
`requestCount` still 0 on the fiftieth. A fourth case seeds the rows the limiter
is waiting for and shows it does block — the arithmetic was never the problem.

### The fix
`consume_rate_limit(identifier, endpoint, max_requests, window_minutes)` over
`rate_limit_state`, which has existed since `20250703165323` for exactly this
and has never been written by anything. `pg_advisory_xact_lock` on
`hashtextextended(identifier || ':' || endpoint, 0)` before the
read-modify-write, so two concurrent requests can't both read the same count and
both pass — the specific failure a limiter exists to prevent, and the one that
gets worse the harder someone pushes. The lock means no unique index, so no lock
on a pre-existing table and the CONCURRENTLY question never arises.

EXECUTE revoked from PUBLIC and granted to `service_role` alone: a function any
client could call would let one caller burn another's quota by passing their IP.
Three callers were handing over a user-JWT client and were converted —
`setup-mfa`, `data-subject-delete` (×2), `data-subject-export` (×2).

Still fails open on a database error, deliberately. But loudly. Failing open
silently is how this survived.

## US-308 — the suite could not finish

A full run took 1490s and reported two `Worker exited unexpectedly` errors, with
one worker at 4.7 GB RSS. Rather than guess, I timed all 110 test files
individually. Exactly two never finished:

    src/components/accessibility/__tests__/AccessibleForm.a11y.test.tsx
    src/pages/__tests__/Settings.a11y.test.tsx

Same bug in both: a `useEffect` whose dependency is an object recreated on every
render. Effect runs, sets state, re-renders, produces another fresh object,
effect runs. React doesn't raise "Maximum update depth exceeded" for this shape
— that guard counts nested synchronous updates inside one commit, and an
effect-driven loop schedules each iteration in its own task. So it spins instead
of erroring, which is why it presents as a hang rather than a failure.

### AccessibleForm
`initialErrors = {}` is a **default parameter**, and the effect depended on it:

    useEffect(() => { setErrors(initialErrors); }, [initialErrors]);

Every caller who omits the prop hands the component a fresh `{}` each render.

I bisected it rather than assuming, because my first reading said the form alone
should loop too, and it doesn't:

    form + <div/>, default initialErrors        passes, 16ms
    form + field, initialErrors pinned          passes, 12ms
    form + field, default initialErrors         never returns

Fixed by comparing serialized content with a ref guard, so the mount doesn't
re-set what `useState` already seeded. `registerField`/`unregisterField` also
built a new `Set` unconditionally; they now return `prev` when nothing changed —
not the loop itself, but fuel for it.

### Settings
The test mocked `useAuth` with inline object literals, so every render produced
fresh `user` and `userProfile`, and the page's access-check effect — which calls
`navigate()` and `toast()` — re-fired forever. The real `AuthContext` memoises
its value (`AuthContext.tsx:1202`), so that mock was modelling something that
cannot happen.

Hoisted the objects. Also changed `role` from `admin` to `root_admin`:
`src/pages/admin/Settings.tsx` is root_admin-only, so every test in that file had
been exercising the redirect rather than the page it claims to test. Four tests
that asserted things about a page they never rendered.

And narrowed the page effect to `[user?.id, userProfile?.role, loading,
navigate]`. An effect with side effects that keys on object identity re-fires for

## US-296 — the guard found the real bug, not the stubs

Deleted `MFASetupDialog.tsx` and `TwoFactorAuth.tsx`. Both unreferenced, both

    supabase/functions/verify-mfa-setup/index.ts:19

So the fourth would have survived the purge *and* the check would have returned

## US-263 — db:types could destroy the file it was regenerating

The script was:

    supabase gen types typescript --project-id brikly > src/integrations/supabase/types.ts

Shell redirection truncates the target **before** the command runs. Any failure
— no network, expired token, wrong project id, CLI not installed — left a
41,282-line types file at zero bytes and the app uncompilable. The failure mode
was strictly worse than not running it.

`scripts/gen-supabase-types.mjs` generates to a temp file, checks it, and only
then moves it into place. The checks matter because the CLI can exit 0 having
printed an auth error or an empty schema, and either replacing 41k lines looks
exactly like success until the build falls over. Verified three failure paths
leave `types.ts` byte-identical: CLI absent, CLI exiting 0 with an auth error,
CLI exiting 0 with a two-table schema.

### AC4, measured
`npx tsc --noEmit -p tsconfig.app.json`: **1842** errors total, against the 1860
baseline. TS2339 is **341**, not the 396 this story recorded — that gap is

    src/components  133
    src/hooks        84
    src/services     64
    src/pages        55
    src/lib           5

Across 57 files. 42 of them contain a `from(…)` or `.rpc(…)`; 15 do not. Those

## Mining the small TS classes again — and being wrong about it

Earlier today I wrote that TS2554 and TS2532 "are worth the same treatment" as
TS2551, which had contained a live bug class. That prediction was mostly wrong.
Across the whole tail below five occurrences — twenty-two error codes — two were

**Real.** `CRMDashboard.tsx:334` called `loadCRMData()` with no argument.

are TanStack Query v5 callback arity drift. `InvoiceList:495` passes 2 of 3 args

## US-241 — the find was not a schema gap

Took the money functions first: `process-refund`, `store-stripe-keys`,
`remove-payment-method`, `set-default-payment-method`. Backlog 132 → 128, all in
report mode via `validateBody`, so nothing 400s until `INPUT_VALIDATION_MODE`
flips.

**`remove-payment-method` had a cross-customer hole.** It authenticated the
caller and then called `stripe.paymentMethods.detach(payment_method_id)` on
whatever id the body carried, with no check that the method belonged to them.
The Stripe key there is the platform's own, so every customer is in scope. Any
signed-in user who learned another customer's `pm_` id could detach it and break
their next renewal.

`detach()` offers no protection of its own. `set-default-payment-method` is safe
only by accident — `customers.update` rejects a method not attached to that
customer. The fix resolves the caller's company `stripe_customer_id`, retrieves
the method, and compares, returning the *same* 404 as a genuine miss, because a
distinct 403 would confirm the id exists.

Worth stating plainly: **adding Zod would not have caught this.** A well-formed
`pm_` id belonging to someone else passes every schema I could write. Validation
and authorisation are different problems, and this story only covers one.

**A real schema gap too.** `process-refund` took `amount` as an unbounded
number, and the approval gate is `amount > 100` — so a *negative* amount is
false for that test, skips approval entirely, and lands in the refunds ledger as
a negative row. Now positive, two decimal places, ceiling 1,000,000.

`store-stripe-keys` was already well authorised — it checks the caller's own
profile company against `company_id` and requires admin. Its gap was shape only:
`secret_key` was unvalidated and would have been encrypted and stored as
whatever it was, surfacing when a charge failed. Now pattern-matched.

### The authorisation lens, applied to the rest
The payments batch paid off by looking at authorisation rather than schemas, so
I wrote a scan for the shape that matters: a value destructured from
`req.json()` reaching `.eq('company_id'|'user_id'|'tenant_id'|…, X)`. 44 sites
across ~20 functions.

Most are harmless — they use a user-JWT client, so RLS enforces the tenancy no
matter what the body claims. Exactly two used a **service-role** client with a
body-supplied id and no caller check.

**`send-push-notification`.** Authenticated the caller, then looked up
`push_subscriptions` for a body `user_id` with the service role. Any signed-in
user could push an arbitrary `title`, `body`, `icon` and `data` payload to *any*
other user — a phishing message delivered through Brikly's own notification
channel, on the lock screen, with Brikly's icon. Now resolves both profiles in
one query and requires the same `company_id`, returning the existing
no-subscriptions response rather than a distinct error, so it can't be used to
probe which user ids exist.

**`social-post-redeploy` had no authentication at all.** Straight from
`req.json()` to a service-role client filtered on the body's `company_id`.

It isn't in `supabase/config.toml`, so `verify_jwt` defaults to true — and that
looked like cover. It isn't. `verify_jwt` means *presents a valid project JWT*,
and **the publishable anon key is one**, and it ships in the client bundle. So
anyone holding the anon key could name any `company_id`, read that company's
`automated_social_posts_config` including its `webhook_url` plus their last
twelve social posts, and fire their webhook.

That distinction is the thing worth carrying out of this: `verify_jwt` is a
gateway signature check, not authentication. Treating it as the latter is
exactly how this function looked covered.

Backlog 128 → 126.

### Generalising the verify_jwt finding
Rather than fix one more function by hand, I swept every edge function for
handler-level caller verification. 46 have none. Most are anonymous by design —
signup and OTP, OAuth and SAML callbacks, lead capture, health-check.

Two were not, and both were reachable on the anon key alone:

`webhook-trigger` took `tenant_id` from the body with a service-role client and
read *and fired* every `webhook_endpoint` for that tenant. Enumerate any
customer's webhook URLs, then post arbitrary data into their downstream systems.

`send-usage-alert` took `companyId` the same way and read every admin email
address for that company before emailing them. Harvest admin addresses per
company, and send them Brikly-branded mail.

Neither had a live caller. Nothing invokes `webhook-trigger` at all, and
`send-usage-alert`'s only invocation is **commented out** in `track-usage`. Dead
code, still deployed, still answering.

Both now require `requireInternalCaller`: service-role bearer or `CRON_SECRET`
header, and it **never fails open** when neither is configured — a misconfigured
internal endpoint should be unreachable, not public. It answers 404 rather than
403 so the endpoint isn't confirmed to exist. Seven tests, including the
anon-key case that `verify_jwt` would have waved through.

### The sentence that hid all of it
`check-edge-function-auth.mjs` opened with:

> Supabase enforces a valid JWT for functions with verify_jwt = true (the
> default).

True, and load-bearing in the wrong direction. It reads as "those are covered",
which is why the guard only ever looked at the 33 `verify_jwt = false` functions
and this class went unexamined. Corrected in place to say what `verify_jwt`
actually is — a signature check the anon key satisfies — and to name the guard
that covers the gap.

`check-unauthenticated-edge-functions.mjs` is that guard: 27 public-by-design,
16 grandfathered and still needing the public / internal / user-auth decision.
Mutation-tested with a new unauthenticated function.

### An open mail relay
Four of the sixteen grandfathered functions are invoked from the browser by a
signed-in user, so the answer for them is user auth rather than internal-only.

`send-notification` is the worst. It takes `to` as a body-supplied email address
and sends through Resend as `Brikly <notifications@resend.dev>`, with no auth at
all. Anyone holding the anon key had an **open mail relay on Brikly's Resend
account and sending reputation** — arbitrary recipient, arbitrary subject and
body, Brikly's name on it. Past the obvious phishing use, that is how a sending
domain gets blacklisted.

It already had a careful Zod schema — `to: z.string().email()`, the lot. That
helped not at all. Every field was well-formed; the missing check was *who*, not
*what*. Third time today that distinction has decided a finding.

`send-support-notification` is the same shape twice over — it mails
`support@brikly.net` and a body-supplied `customerEmail`. `send-safety-
notification` sends incident mail under Brikly's name to body-named addresses.
`document-classifier` spends money per call on a model provider.

All four now call `initializeAuthContext`. Baseline 16 → 12.

Of the twelve left, `blog-ai-automation`, `seo-backend-integration` and
`trigger-expo-build` have no caller anywhere in the repo, so internal-only is
probably right for them.

### Finishing the triage, and getting it wrong first
The guard baseline is empty now: every edge function verifies its caller, inside
its handler. Split by what actually invokes each — five browser-invoked got
`initializeAuthContext`, two invoked by another edge function with a service-role
client got `requireInternalCaller` (both verified to pass that bearer before I
required it), five with no caller anywhere got `requireInternalCaller`.

**I added two of them in the wrong place.** Applying the checks by script, the
ones for `social-content-generator` and `blog_social_webhook` landed inside
helper functions — `getRecentFormats`, `getInstagramMediaFromStorage` — rather
than the handlers. They compiled, because `req` was in scope through the
closure. And the guard, which matched on name only, reported both as covered.

A check that runs in the wrong function is worse than none, because it reads as
done. I caught it by verifying separately that each guard call sits after the
handler declaration — not by trusting the guard I had just written.

So the guard enforces that itself now, on the AST: locate the handler passed to
`serve()` / `Deno.serve()` / assigned to a handler variable, and require the
guard call lexically inside it.

That immediately flagged five more. Four were my own detector missing
`Deno.serve` — a `PropertyAccessExpression`, not a bare identifier. The fifth,
`api-management`, was genuine delegation: every route function validates a
hashed API key through `validateApiRequest`, and only `createApiKey` uses
`auth.getUser`. Both are real caller verification; my pattern just didn't know
the first one.

The delegation exemption is a `DELEGATES` map that names the delegate and
requires it to contain the check — deliberately **not** a blanket "one level of
delegation is fine" rule, because that rule would have accepted the two real
misplacements this whole check exists for.

## US-248 — reconciling the two scripts nobody wanted to delete

AC2 said delete `repair-migrations.ps1` and `mark-applied.ps1` "after history is
reconciled and documented", and nobody had done the reconciling. It takes a

    mark-applied lists 345 timestamps, all 345 have a local file    (no orphans)
    repair reverts 193 timestamps, none of them exist locally       (consistent)
    60 local migrations appear in neither, all from 20251202 on     (added after)

Internally consistent, which is the case for deleting both.

What it does **not** establish, and the runbook says so plainly: that those 345
were ever *executed* against production. `migration repair --status applied`
records history without running SQL. If a table or column a migration should
have created turns out to be missing in prod, that is the first place to look.

**AC1** — `docs/RUNBOOK_MIGRATION_DEPLOY.md`. Clean detached checkout of the
merge commit, staging first, `migration list` read before every push, and the

tool, and reaching for it is an incident, not a step.

**AC3** — `scripts/check-migration-drift.sh`. Fails on drift in *either*
direction: a remote-only entry means SQL ran that isn't in the repo, a local-only
entry means a deploy didn't finish. It exits 0 with a message when the CLI is
absent rather than pretending to pass, and refuses to report clean if the CLI's
output shape isn't what it expects.

**AC4** — `scripts/check-no-migration-repair.sh`, in pre-commit and CI. It took
three passes. The first scanned every tracked file and flagged `prd.json` for

in its own match pattern and the other in its error text. A guard cannot be
forbidden from naming the thing it guards against.

Final shape: scoped by file type, comment lines stripped so documenting the rule
anywhere needs no entry, and exactly two bounded exemptions — the historical
scripts until AC2 deletes them, and the two guard scripts themselves.
Mutation-tested both ways: a real command in a shell script is caught, a comment
mentioning it is not.

## US-303: the calculator funnel has never captured a lead

The story asked whether lead scoring is a feature. It is: `/calculator` and
`/profitability-calculator` are live marketing routes. So the two missing
functions get written rather than the call sites deleted. Writing them turned
out to be the small half.

I stood up Postgres 16 locally, applied
`20250710000000_profitability_calculator_leads.sql` (the only migration that
touches these tables), and ran the visitor journey as the `anon` role. Three
separate failures reproduce, none of which any test or type could have seen:

    INSERT INTO calculator_calculations (session_id, ...) VALUES ('calc_1756000000000_abc123xyz', ...)
    ERROR:  invalid input syntax for type uuid: "calc_1756000000000_abc123xyz"

`calculator_calculations.session_id` is a uuid FK to `calculator_sessions(id)`,
but `generateSessionId()` returns `calc_<epoch>_<suffix>` and that is what the
client sends. The error was never read, so no calculation has ever been stored.

    INSERT INTO calculator_leads (email, ...) VALUES ('lead@example.com', ...) RETURNING id
    ERROR:  new row violates row-level security policy for table "calculator_leads"

anon holds INSERT and neither SELECT nor UPDATE. The same statement without
`RETURNING` succeeds; with `ON CONFLICT DO UPDATE` it fails too. The client's
upsert used both, so `trackEmailCapture` threw for every visitor and returned
null, which is why `increment_lead_score` would never have fired even if it had
existed. I had guessed this was a filtered `RETURNING` yielding zero rows and a
`PGRST116`; it is a hard RLS rejection. Both halves verified independently.

    UPDATE calculator_sessions SET pdf_downloaded = true WHERE session_id = '...'
    -- 0 rows, no error

No anon UPDATE policy at all. `get_calculator_funnel_metrics` reads exactly
`email_captured`, `pdf_downloaded`, `trial_clicked` and `calculations_performed`,
so the funnel dashboard has only ever shown zeros.

And `trackReferral` built its update with `supabase.raw('referral_count + 1')`.
There is no `raw()` on the supabase-js v2 client (`typeof client.raw` is
`undefined`), so evaluating the argument threw before `.update()` was reached.

`20260827110000_calculator_lead_scoring.sql` adds six SECURITY DEFINER entry
points instead of the anon UPDATE and SELECT policies the client-side version
would have needed. anon has no identity, so a policy letting it update
`calculator_sessions` is a policy letting anyone update anyone's row. A definer
function does the narrow thing: flip one named boolean, add clamped points to
one lead. `record_calculator_session_event` matches the event name against a
fixed list, so the writable column set is exactly those five.

On AC2's "cannot score another company's leads": `calculator_leads` has no

## US-310: journal entries, bills and bill payments could not be created

The guard from US-303 found this an hour after it was written. All three
mutations open the same way:

    const { data: seqData, error: seqError } = await supabase
      .rpc('nextval', { sequence_name: 'journal_entry_number_seq' });
    if (seqError) throw seqError;

`nextval` is `pg_catalog.nextval(regclass)`. It lives in a schema PostgREST does
not expose, and it takes one regclass argument, not a `sequence_name`. Either
fact alone makes the call unresolvable, and no migration has ever created a
public wrapper. The `throw` on the next line means no journal entry, no vendor
bill and no bill payment has ever been created through this UI. The three
sequences do exist; only the way they were reached was broken.

Fixed with the pattern the repo already uses for every other numbered document,
`generate_po_number` and thirteen siblings: a SECURITY DEFINER `generate_*`
function plus a BEFORE INSERT trigger that fills the column when it arrives
empty. A public `nextval` wrapper would have been fewer lines and would have
handed any authenticated user a way to advance any sequence in the database by
name.

Verified by pulling the real `journal_entries` / `bills` / `bill_payments` DDL
and the three sequences out of `20250707000000_enterprise_finance_module.sql`,
applying them and this migration to Postgres 16, and inserting as
`authenticated`. The trigger assigns JE-001000, BILL-001000, PMT-001000; a
client that supplies its own number keeps it; a blank string is replaced rather
than stored as a document with no number (`NOT NULL` would have accepted `'   '`
happily); and `UNIQUE(company_id, <number>)` still rejects a duplicate within a
company while accepting the same number in another.

Then `apply_bill_payment`, which I had baselined an hour earlier as "the call
site already falls back safely". That reasoning stops holding the moment
payments become possible. Before this fix the mutation threw on `nextval` and
the fallback never ran; after it, the fallback is the live path, and it reads
`amount_paid` off the client's loaded copy of the bill and writes back the sum.
Two payments applied to one bill at once both read the same value and both write
the same total. One of them disappears, in a ledger.

It is now one UPDATE, so the read and the write happen under the lock the UPDATE
itself takes:

    SET amount_paid = COALESCE(amount_paid, 0) + p_amount

Proven with two overlapping sessions rather than asserted: the second caller
blocked 1530ms on the row lock and applied on top, leaving 600.00 rather than
300.00. SECURITY DEFINER bypasses RLS, so tenancy is enforced inside the
function with `user_in_company`, which also requires an active profile. Another
company's bill answers "bill not found" rather than "forbidden", because
confirming that a given bill id exists is itself a leak. Also verified: open ->
partial -> paid across two payments, a voided bill not flipped to paid, a zero
or negative amount refused, a deactivated profile in the right company refused,
and the other company's bill untouched at 0.00.

The `check-rpc-definitions.mjs` baseline is now empty. Both of its entries went
stale within an hour of being written, and the guard caught both, which is what
the only-shrinks rule exists for. It also learned to strip comments before
scanning: the migration and the tests here quote the broken `nextval` call in
prose, and the first run flagged my own test file for describing the bug. That
is the same lesson `check-no-migration-repair.sh` taught in US-248 and I walked
into it again. Mutation-tested four ways: a real call to a missing name is
caught, the same name in a line comment and in a block comment is not, and a URL
on the same line as a real call does not hide it.

Not changed, and worth a decision rather than inheritance: the sequences are
global while uniqueness is per company, so two companies creating journal
entries interleave and each sees gaps. Company A got JE-001000, JE-001002,
JE-001003 while company B took JE-001001. Every other numbered document here
already behaves this way, so singling out journal entries would be inconsistent,
and gap-free per-company numbering needs a counter table and a decision about
existing rows. Auditors do test journal-entry sequences for gaps.

25 cases in `src/hooks/__tests__/accountingWritePaths.test.ts`, mutation-tested
six ways. Full suite: 121 files, 2685 passing, 2 skipped, 28.2s.

## US-272: one pinned version per dependency, and one live bug it was hiding

supabase-js was imported six ways across the edge functions: esm.sh at 2.50.3,
2.49.1, 2.39.3 and 2.39.0, esm.sh at a floating `@2`, and `npm:` at a floating
`@2`. std at 0.168.0 and 0.190.0. zod as both `npm:zod@3` and
`deno.land/x/zod@v3.22.4`. stripe three ways. 151 imports rewritten across 128
files; no `npm:` specifier and no floating version is left.

The floating specifiers are the obvious half: `@2` resolves at cold start, so
the version a function runs is whatever was published most recently and nothing
records which. The half that mattered more is the loader split.

Deno keys module instances by resolved specifier, so `npm:zod@3` and
`https://deno.land/x/zod@v3.22.4/mod.ts` were two module graphs holding two
distinct `ZodError` classes. `_shared/validation.ts` line 23:

    if (error instanceof z.ZodError) {

with `z` from `npm:zod@3`. Every one of its nine callers built their schemas with
the deno.land copy: `setup-mfa`, `verify-mfa-setup`, `verify-mfa-login`, all four
`sso-*` endpoints, `create-stripe-checkout` and `process-invoice-payment`, across
21 call sites. The check was false on every request, so `validateRequest` fell to
its generic branch and answered `'Invalid request format'` instead of naming the
field that failed. MFA enrolment, MFA login, every SSO configuration endpoint and
two payment endpoints.

I demonstrated it rather than reasoning about it, loading two copies of zod under
different module identities:

    thrown by copy A. instanceof A.ZodError: true
                      instanceof B.ZodError: false
    err.errors is still readable: true -> Invalid uuid
    same class object? false

That last line is the whole thing. Nothing about it is visible in the source of
either file: both import `z`, both use it correctly, and the type checker is
satisfied because the two copies are structurally identical.

`_shared/validate-body.ts` was not affected, and the reason is worth keeping: it
reads `result.error.errors` off `safeParse` and never uses `instanceof`. That is
the safer shape whenever a schema crosses a module boundary.

`ai-service-v2.ts` is now `ai-service-env.ts`. The two are not a version pair:
`ai-service.ts` reads the `ai_model_configurations` table the admin UI writes to
and serves four production functions, while the other reads Coolify team shared
variables. A name saying "v2" reads as the one to reach for, and reaching for it
would move a feature off the DB-configured models without anyone noticing.

`auth-helpers-single-tenant.ts` is deleted; its only reference in the tree was
its own usage example. I had it wrong at first: I assumed from the name that it
dropped `company_id` scoping, and the diff says otherwise. It has the same
`verifyCompanyAccess` with the same scoping. What it actually was is a stale
fork, still importing `npm:@supabase/supabase-js@2` and missing
`safeErrorResponse` - the US-242 fix that stops a 500 handing the client raw
Postgres error text naming schema, columns and constraints. Which is a better
example of the US-302 hazard than the one I invented: someone reads
"single-tenant", picks it on the name, and gets last quarter's copy without the
fix.

`scripts/check-deno-imports.mjs` requires a full `x.y.z` on every remote import,
and requires every import of a package `deno.json` names to use exactly that
specifier. The second rule is what catches a loader split, which is the shape
that caused the zod bug and which a per-package version check would pass.
Mutation-tested five ways, including a string-literal URL that must *not* fail.

What I could not do: there is no Deno toolchain here and no CI deploy for edge
functions, so none of this was type-checked or executed under Deno. The evidence
for each target version is that it is what the largest group of functions was
already running in production - 80 on supabase-js 2.50.3, 75 on std 0.190.0, 17
on zod v3.22.4, 14 on stripe 14.21.0. Every std import across the whole tree was
`{ serve }` from `http/server.ts` at both versions, and the five `npm:stripe@14`
functions construct the client identically to the fourteen esm.sh ones. That is
as far as static evidence goes; one function per package deserves a smoke test
after the next deploy.

15 cases in `supabase/functions/_shared/deno-imports.test.ts`, mutation-tested
four ways. Full suite: 122 files, 2700 passing, 2 skipped, 29.4s.

Staging 128 previously-untouched edge functions put them through `lint-staged`
